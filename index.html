Approach · DevX Lead

How I decide what to automate

I listed the recurring tasks run by IT and by the business, with the time each one takes on both sides and the risks it carries. For each task I asked one question: can it be automated, or should it move to PowERTools and be improved so the business takes control and gains autonomy?

Inventory

List every recurring task, with the time it takes on the IT side and on the business side.

Assess

Rate the risks: errors, delays, downtime and the lack of traceability.

Decide

Automate it if it can run hands-off. Otherwise move it to PowERTools and improve it so the business runs it.

The decision

Experience · Occupational health software

Connector CLI: migrating uEgar classic to uEgar.neo

A command-line bridge between a legacy occupational health application and its new microservices platform. It reads the old database, turns data into messages and delivers them reliably, in dependency order.

.NET Framework 4.6.2SQL ServerOutbox patternHTTP + JWTSerilogWindows scheduled task

Challenge

  • Two systems with different models: a legacy application on SQL Server and new microservices
  • Entities depend on each other, so the order of migration matters
  • Delivery must survive outages of the new platform
  • Unique e-mails and shared reference data had to be handled before the switch

Solution

Command-line tool

A .NET command-line tool that reads the legacy database, turns data into messages and delivers them to the new microservices with the Outbox pattern, bounded retries and automatic purge.

Impact

  • No message lost if the new platform is down
  • Ordered export with parallelism inside each level
  • One failing export never contaminates another
  • Runs unattended as a Windows scheduled task, with logs and status commands

Demo

Connector CLI · 63 s

How the migration works

  1. ReadThe export command reads the legacy SQL Server database.
  2. TransformEach entity becomes messages, exported in seven ordered passes.
  3. BufferMessages go to an Outbox table, or to a JSON dump with the file option.
  4. DeliverThe outbox command polls, retries and purges in three parallel loops.
  5. ReceiveAbout thirty Neo microservices get the messages over HTTP with a JWT.

Options: a filter to target a list of ids (GUID or employee number), a batch size, and a force flag to replay an export already done.

Phase 0 · Prepare

  • info checks the database and service URLs
  • security -e encrypts secrets
  • set-user-email generates unique e-mails
  • link binds the legacy domain to Neo
  • lock-repositories avoids two sources of truth

Phase 1 · Export

  • export --all or targeted with -e
  • 7 passes, one subprocess per type
  • --filter to target a list of ids
  • --force to replay an export

Phase 2 · Send to Neo

  • outbox -wp -wr runs continuously
  • Started by a Windows scheduled task at server start
  • outbox --info as a dashboard

Phase 3 · Cutover

  • close-medical-visits closes the existing medical visits in the legacy application

Sensitive commands (link, lock-repositories, set-user-email) show a warning, ask for confirmation, the admin password and an OTP when enabled.

A structured request goes in, the work runs on its own, every run is logged. Happy to walk through any of it in more detail.

Expérience · Logiciel de santé au travail

Connector CLI : migrer uEgar classic vers uEgar.neo

Un pont en ligne de commande entre une application legacy de santé au travail et sa nouvelle plateforme de microservices. Il lit l’ancienne base, transforme les données en messages et les livre de façon fiable, dans l’ordre des dépendances.

.NET Framework 4.6.2SQL ServerOutbox patternHTTP + JWTSerilogTâche planifiée Windows

Défi

  • Deux systèmes aux modèles différents : une application legacy sur SQL Server et de nouveaux microservices
  • Les entités dépendent les unes des autres, l’ordre de migration compte
  • La livraison doit résister aux pannes de la nouvelle plateforme
  • E-mails uniques et référentiels partagés à traiter avant la bascule

Solution

Outil en ligne de commande

Un outil .NET en ligne de commande qui lit la base legacy, transforme les données en messages et les livre aux nouveaux microservices avec le pattern Outbox, des reprises bornées et une purge automatique.

Impact

  • Aucun message perdu si la nouvelle plateforme est en panne
  • Export ordonné avec parallélisme à chaque niveau
  • Un export en échec ne contamine jamais un autre
  • Tourne sans surveillance comme tâche planifiée Windows, avec logs et commandes de statut

Démo

Connector CLI · 63 s · vidéo en anglais

Comment fonctionne la migration

  1. LireLa commande d’export lit la base legacy SQL Server.
  2. TransformerChaque entité devient des messages, exportés en sept passes ordonnées.
  3. Mise en tamponLes messages vont dans une table Outbox, ou dans un dump JSON avec l’option file.
  4. LivrerLa commande outbox interroge, relance et purge dans trois boucles parallèles.
  5. RecevoirEnviron trente microservices Neo reçoivent les messages en HTTP avec un JWT.

Erfahrung · Software für Arbeitsmedizin

Connector CLI: Migration von uEgar classic zu uEgar.neo

Eine Kommandozeilenbrücke zwischen einer Legacy-Anwendung für Arbeitsmedizin und ihrer neuen Microservice-Plattform. Sie liest die alte Datenbank, wandelt Daten in Nachrichten um und liefert sie zuverlässig in Abhängigkeitsreihenfolge.

.NET Framework 4.6.2SQL ServerOutbox patternHTTP + JWTSerilogGeplante Windows-Aufgabe

Herausforderung

  • Zwei Systeme mit unterschiedlichen Modellen: eine Legacy-Anwendung auf SQL Server und neue Microservices
  • Entitäten hängen voneinander ab, die Reihenfolge der Migration ist entscheidend
  • Die Zustellung muss Ausfälle der neuen Plattform überstehen
  • Eindeutige E-Mails und gemeinsame Referenzdaten mussten vor der Umstellung geklärt werden

Lösung

Kommandozeilentool

Ein .NET-Kommandozeilentool, das die Legacy-Datenbank liest, Daten in Nachrichten umwandelt und per Outbox-Pattern an die neuen Microservices liefert, mit begrenzten Wiederholungen und automatischer Bereinigung.

Wirkung

  • Keine Nachricht geht verloren, wenn die neue Plattform ausfällt
  • Geordneter Export mit Parallelität innerhalb jeder Stufe
  • Ein fehlgeschlagener Export beeinflusst nie einen anderen
  • Läuft unbeaufsichtigt als geplante Windows-Aufgabe, mit Logs und Statusbefehlen

So funktioniert die Migration

  1. LesenDer Export-Befehl liest die Legacy-SQL-Server-Datenbank.
  2. UmwandelnJede Entität wird zu Nachrichten, exportiert in sieben geordneten Durchläufen.
  3. PuffernNachrichten gehen in eine Outbox-Tabelle oder mit der Option file in einen JSON-Dump.
  4. LiefernDer Outbox-Befehl pollt, wiederholt und bereinigt in drei parallelen Schleifen.
  5. EmpfangenRund dreißig Neo-Microservices erhalten die Nachrichten per HTTP mit JWT.

Optionen: ein Filter für eine Liste von IDs (GUID oder Personalnummer), eine Batch-Größe und ein Force-Flag, um einen bereits erfolgten Export zu wiederholen.
